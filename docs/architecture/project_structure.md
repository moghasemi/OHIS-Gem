# معماری ساختار مخزن OHIS (Monorepo Specification)
## فاز ۶.۲ — Project Skeleton

### ۱. اصل تفکیک Monorepo
سامانه OHIS بر اساس الگوی معماری **Modular Monolith** با رویکرد **DDD-ready** و تفکیک لایه‌ای طراحی شده است. ساختار مخزن به صورت مونو‌ریپو متمرکز بوده و شامل بخش‌های زیر است:

```text
OHIS/
├── .github/workflows/ci.yml       # خط‌لوله CI یکپارچه با پین Commit SHA و حداقل مجوزها
├── pytest.ini                     # تنظیمات رسمی آزمون‌های سطح سیستم
├── backend/                       # سرویس جنگو (Modular Monolith)
│   ├── manage.py                  # مدخل خط فرمان جنگو با پشتیبانی dotenv
│   ├── Dockerfile                 # تصویر پایتون ۳.۱۱.۱۸ و نصب مقید با constraints
│   ├── config/                    # تنظیمات کلان، روتینگ، WSGI/ASGI و Celery
│   │   ├── settings/              # تفکیک محیط‌ها (base, development, testing, staging, production)
│   ├── core/                      # هسته معماری و مدل‌های انتزاعی پایه (TimeStampedModel)
│   ├── common/                    # ابزارها و کدهای عمومی کمکی مشترک
│   ├── apps/                      # ماژول‌های دامنه‌ای سیستم (clinical, ...)
│   ├── requirements/              # نیازمندی‌های تفکیک‌شده به همراه constraints.txt
│   ├── media/                     # ذخیره‌سازی فایل‌های بارگذاری‌شده
│   └── static/                    # فایل‌های استاتیک جنگو
├── frontend/                      # کلاینت React 19 + TypeScript + Vite با مدیر بسته Bun
│   ├── src/                       # ماژول‌ها، کامپوننت‌ها و صفحات وب
│   ├── public/                    # دارایی‌های عمومی و فایل‌های راهنما
│   ├── package.json               # تنها مانیفست وابستگی در کل مخزن
│   ├── bun.lock                   # فایل قفل وابستگی Bun (منجمد)
│   ├── tsconfig.json              # کانفیگ TypeScript فرانت‌اند
│   └── vite.config.ts             # کانفیگ بیلد Vite
├── infrastructure/                # فایل‌ها و مانیفست‌های زیرساختی
├── deployment/                    # تنظیمات و اسکریپت‌های استقرار داکر
├── docs/architecture/             # اسناد معماری، ماتریس متغیرها و راهنماها
├── tools/                         # اسکنر جامع اسرار و ابزارهای کیفی
└── tests/integration/             # آزمون‌های سطح سیستم و اثبات سلامت دیتابیس/ردیس
```

### ۲. قوانین مرزبندی ماژول‌ها
- **`backend/core/`**: صرفاً کدهای زیربنایی معماری سامانه. در فاز ۶.۲ تنها کلاس انتزاعی `TimeStampedModel` در آن قرار دارد. کلاس‌های مربوط به Multi-Tenancy، RBAC و قوانین حسابرسی (Audit) متعلق به فاز ۶.۳ می‌باشند.
- **`backend/common/`**: توابع و ابزارهای عمومی بدون منطق بالینی (مانند اعتبارسنجی ارقام چک کد ملی، نرمال‌سازی حروف فارسی).
- **`backend/apps/`**: اپلیکیشن‌های دامنه‌ای سیستم. در این فاز ماژول `clinical` بدون تغییر در دامنه حفظ شده است.
- **`frontend/`**: کلیه کدهای کلاینت منحصراً در این دایرکتوری قرار داشته و وابستگی‌های آن با دستور `bun install --frozen-lockfile` مدیریت می‌شود.

### ۳. محدودیت مستندشده محیط‌های توسعه ابری (Cloud Developer Previews)
محیط‌های پیش‌نمایش خودکار ابری (مانند ناظر پورت ۳۰۰۰ در Google AI Studio) در حالت پیش‌فرض برای اجرای سرور به دنبال `package.json` در دایرکتوری ریشه می‌گردند.  
پیرو تصمیم مصوب حاکمیت پروژه مبنی بر حفظ مونو‌ریپوی خالص و استقرار تنها یک `package.json` در `frontend/`، توسعه‌دهندگان می‌توانند سرویس فرانت‌اند را به صورت مستقیم با دستورات زیر اجرا و مدیریت نمایند:
```bash
bun --cwd frontend run dev
bun --cwd frontend run build
bun --cwd frontend run typecheck
```
این تفکیک تضمین می‌کند که مخزن بدون هیچ فایل موازی یا وابستگی تکراری آماده استقرار سازمانی و اجرای پایپ‌لاین‌های CI/CD باشد.
